# Методология расчёта метрик Yambda

## 1. Исходные события

Одна строка исходных данных — одно событие пользователя `uid` над треком
`item_id` в момент `timestamp`.

| `event_type` | Событие |
|---|---|
| `listen` | прослушивание |
| `like` | установка лайка |
| `dislike` | установка дизлайка |
| `unlike` | удаление лайка |
| `undislike` | удаление дизлайка |

Установка и удаление реакции считаются отдельными событиями. Например,
последовательность `like` → `unlike` даёт одно событие `like` и одно событие
`unlike`. Счётчик `like` при удалении не уменьшается.

### День наблюдения

```text
day_idx = timestamp // 86400
observation_day = day_idx + 1
```

`day_idx` используется в витринах. `observation_day` добавляется при экспорте в
DataLens и нумерует дни от 1.

### Прослушивание

```text
is_listen = event_type = 'listen'
```

### Источник прослушивания

Источник учитывается только для событий `listen`:

```text
is_organic = 0 → прослушивание из рекомендаций
is_organic = 1 → органическое прослушивание
```

### Listen+

```text
is_listen_plus =
    event_type = 'listen' AND played_ratio_pct > 50
```

Прослушивание ровно 50% трека не считается Listen+.

### Повтор

```text
is_replay =
    event_type = 'listen' AND played_ratio_pct > 100
```

Прослушивание ровно 100% трека не считается повтором.

### Время прослушивания

Для события `listen`:

```text
play_seconds = track_length_seconds × played_ratio_pct / 100
```

Для остальных типов событий `play_seconds = NULL`. Значение не ограничивается
длительностью трека, поэтому при `played_ratio_pct > 100` оно может быть больше
`track_length_seconds`.

### Сессия

Для каждого пользователя события сортируются по `timestamp`, затем по
`item_id` и `event_type`.

Событие начинает новую сессию, если оно первое для пользователя или если после
предыдущего события прошло больше 1800 секунд:

```text
is_session_start =
    previous_timestamp IS NULL
    OR timestamp - previous_timestamp > 1800
```

В расчёте участвуют все события, включая реакции. Интервал ровно 1800 секунд не
начинает новую сессию.

## 2. Дневные продуктовые метрики

Одна строка `mart_product_day` соответствует одному `day_idx`.

### Счётчики

| Метрика | Точное определение |
|---|---|
| Активные пользователи, DAU | число уникальных `uid` с любым событием в этот день |
| Слушатели | число уникальных `uid` хотя бы с одним `listen` в этот день |
| Прослушивания | число событий `listen` |
| Уникальные треки | число уникальных `item_id` среди событий `listen` |
| Listen+ | число событий с `is_listen_plus = true` |
| Прослушивания из рекомендаций | число `listen` с `is_organic = 0` |
| Органические прослушивания | число `listen` с `is_organic = 1` |
| Повторы | число событий с `is_replay = true` |
| Лайки | число событий `like` |
| Дизлайки | число событий `dislike` |
| Сессии | сумма `is_session_start` |

### Доли

Все формулы ниже рассчитываются отдельно для каждого дня.

```text
Доля Listen+ =
    количество Listen+ / количество прослушиваний

Доля повторов =
    количество повторов / количество прослушиваний

Доля рекомендаций =
    прослушивания из рекомендаций / все прослушивания

Listen+ рекомендаций =
    Listen+ из рекомендаций / прослушивания из рекомендаций

Listen+ органики =
    Listen+ из органики / органические прослушивания

Повторы рекомендаций =
    повторы из рекомендаций / прослушивания из рекомендаций

Повторы органики =
    повторы из органики / органические прослушивания
```

### Реакции

```text
Лайки на 1000 прослушиваний =
    количество событий like × 1000 / количество прослушиваний

Дизлайки на 1000 прослушиваний =
    количество событий dislike × 1000 / количество прослушиваний
```

Для доли слушателей с реакцией сначала на уровне `uid + day_idx` проверяется:

- было ли хотя бы одно прослушивание;
- было ли хотя бы одно событие `like` или `dislike`.

Затем рассчитывается:

```text
Доля слушателей с лайком =
    слушатели с ≥ 1 like в этот день / все слушатели этого дня

Доля слушателей с дизлайком =
    слушатели с ≥ 1 dislike в этот день / все слушатели этого дня
```

Прослушивание и реакция должны принадлежать одному пользователю и одному дню,
но не обязательно одному треку.

### Время на активного пользователя

```text
Минуты на активного =
    сумма play_seconds / число активных пользователей / 60
```

### KPI текущего продуктового дашборда

Для выбранного набора дней:

```text
Средний DAU = AVG(active_users)

Средние прослушивания в день = AVG(listens)

Прослушиваний на активного =
    SUM(listens) / SUM(active_users)

Доля рекомендаций =
    SUM(recommendation_listens) / SUM(listens)
```

Без фильтров по 301 дню формулы дают `3 574,71`, `154 376,12`, `43,1856` и
`48,3428%`. После округления это значения карточек `3 575`, `154 376`, `43,19`
и `48,3%`.

В приложенном описании приведена более ранняя конфигурация продуктового
дашборда с медианным DAU. Она не соответствует текущему скриншоту.

## 3. Пользовательские метрики

Одна строка `mart_user` соответствует одному `uid` за весь период.

| Метрика | Точное определение |
|---|---|
| Первый день | минимальный `day_idx` среди всех событий пользователя |
| Последний день | максимальный `day_idx` среди всех событий пользователя |
| Активные дни | число уникальных `day_idx` с любым событием пользователя |
| Прослушивания | число событий `listen` |
| Уникальные треки | число уникальных прослушанных `item_id` |
| Listen+ | число прослушиваний больше 50% |
| Рекомендации | число прослушиваний с `is_organic = 0` |
| Повторы | число прослушиваний больше 100% |
| Лайки / дизлайки | число событий `like` / `dislike` |
| Удаления реакций | число событий `unlike` / `undislike` |
| Сессии | сумма `is_session_start` |

```text
Доля Listen+ пользователя = Listen+ / прослушивания

Доля рекомендаций пользователя =
    прослушивания из рекомендаций / прослушивания

Доля повторов пользователя = повторы / прослушивания

Минуты на сессию = сумма play_seconds / сессии / 60
```

`mart_user_day` использует те же определения на уровне `uid + day_idx`.

## 4. Retention

### Первый день пользователя

Для retention первый день определяется иначе, чем поле `first_day` в
`mart_user`:

```text
cohort_day = минимальный day_idx с событием listen
```

События без прослушивания не определяют начало retention-когорты.

### День жизни

```text
lifetime_day = день прослушивания - cohort_day
```

### Retention Dn

Пользователь удержан на Dn, если у него есть хотя бы одно прослушивание ровно в
день:

```text
cohort_day + n
```

Для одной когорты и одного сегмента:

```text
Retention Dn =
    пользователи с прослушиванием на lifetime_day = n
    / размер когорты
```

Это exact-day retention. Прослушивание позже дня `n` не заменяет отсутствие
прослушивания в день `n`.

Когорта участвует в расчёте Dn только при условии:

```text
cohort_day + n <= максимальный day_idx в данных
```

В исследуемом периоде `day_idx` принимает значения от 0 до 300. Поэтому для
расчёта доступны:

```text
D1:  cohort_day <= 299
D7:  cohort_day <= 293
D30: cohort_day <= 270
```

На дашборде указано дополнительное правило: основные KPI D1, D7 и D30 не
включают пользователей с `cohort_day = 0`. Это правило относится к фильтру
дашборда; внутри `mart_retention_cohort` день 0 присутствует.

При объединении нескольких когорт используется:

```text
Общий Retention Dn =
    сумма retained_users / сумма cohort_users
```

При фильтрах `cohort_day > 0` и `lifetime_day = 1 / 7 / 30` получаются:

```text
D1  = 3356 / 6696 = 50,12%
D7  = 2761 / 6696 = 41,23%
D30 = 2436 / 6402 = 38,05%
```

После округления это значения карточек `50,1%`, `41,2%` и `38,1%`.

### Доля рекомендаций первого дня

```text
Доля рекомендаций первого дня =
    рекомендательные прослушивания в cohort_day
    / все прослушивания в cohort_day
```

| Сегмент | Условие |
|---|---|
| `0%` | доля = 0 |
| `1-25%` | 0 < доля ≤ 0,25 |
| `25-50%` | 0,25 < доля ≤ 0,50 |
| `50-75%` | 0,50 < доля ≤ 0,75 |
| `75-99%` | 0,75 < доля < 1 |
| `100%` | доля = 1 |

### Вовлечённость первого дня

| Сегмент | Число прослушиваний в `cohort_day` |
|---|---:|
| `1-10` | 1–10 |
| `11-30` | 11–30 |
| `31-60` | 31–60 |
| `61+` | 61 и больше |

### Недельная когорта

```text
cohort_week_start = (cohort_day // 7) × 7
```

Например, `cohort_week_start = 7` соответствует группе «Дни 007–013».

## 5. Метрики треков

Одна строка `mart_track` соответствует одному `item_id` за весь период.

Для каждого трека отдельно рассчитываются прослушивания, слушатели, Listen+,
рекомендательные и органические прослушивания, повторы, лайки и дизлайки.

```text
Доля Listen+ трека = Listen+ трека / прослушивания трека

Доля рекомендаций трека =
    рекомендательные прослушивания трека / все прослушивания трека

Listen+ рекомендаций трека =
    Listen+ из рекомендаций / рекомендательные прослушивания

Listen+ органики трека =
    Listen+ из органики / органические прослушивания

Лайки на 1000 =
    события like трека × 1000 / прослушивания трека

Дизлайки на 1000 =
    события dislike трека × 1000 / прослушивания трека

Разница Listen+, п.п. =
    (Listen+ рекомендаций - Listen+ органики) × 100
```

### Надёжная выборка

```text
Надёжная выборка = прослушивания трека >= 100
```

В `track_quality.csv` экспортируются только треки с надёжной выборкой. Фильтр
`1000+ прослушиваний` на карте качества — дополнительный фильтр дашборда, а не
определение надёжной выборки в коде.

В текущем состоянии дашборда фильтр `listens >= 1000` действует на пять KPI:

```text
Надёжная выборка = COUNT(item_id)

Прослушивания = SUM(listens)

Взвешенный Listen+ = SUM(listen_plus) / SUM(listens)

Лайки на 1000 = SUM(likes) × 1000 / SUM(listens)

Дизлайки на 1000 = SUM(dislikes) × 1000 / SUM(listens)
```

По приложенному CSV получаются `8 538` треков, `22 610 930` прослушиваний,
`63,21%` Listen+, `17,94` лайка и `2,05` дизлайка на 1000 прослушиваний.

### Длительность трека

| Сегмент | Условие |
|---|---|
| `до 2 мин` | длительность < 120 секунд |
| `2–3 мин` | 120 ≤ длительность < 180 секунд |
| `3–4 мин` | 180 ≤ длительность < 240 секунд |
| `4–5 мин` | 240 ≤ длительность < 300 секунд |
| `5+ мин` | длительность ≥ 300 секунд |

### Сегменты качества

Пороги рассчитываются по трекам с 100 и более прослушиваниями:

```text
LP25 = 25-й процентиль доли Listen+
LP75 = 75-й процентиль доли Listen+
D75  = 75-й процентиль дизлайков на 1000 прослушиваний
```

```text
Высокое качество:
    Доля Listen+ >= LP75
    AND дизлайки на 1000 < D75

Требует внимания:
    Доля Listen+ <= LP25
    OR дизлайки на 1000 >= D75

Стабильные:
    все остальные треки
```

Условие «требует внимания» имеет приоритет, поскольку в коде этот сегмент
присваивается последним.

## 6. Воронка рекомендаций

Воронка строится за весь период:

| Шаг | События | Пользователи |
|---|---|---|
| Все прослушивания | все события `listen` | уникальные слушатели |
| Прослушивания из рекомендаций | `listen` с `is_organic = 0` | уникальные пользователи рекомендаций |
| Listen+ из рекомендаций | рекомендательные Listen+ | уникальные пользователи с рекомендательным Listen+ |
| Повторы из рекомендаций | рекомендательные повторы | уникальные пользователи с рекомендательным повтором |

Для событий и пользователей отдельно рассчитываются:

```text
Конверсия от начала = значение шага / значение первого шага

Конверсия от предыдущего =
    значение шага / значение предыдущего шага
```

## 7. Проверки и ограничения

### Проверки источника

Сборка останавливается, если:

- есть `NULL` в `uid`, `item_id`, `timestamp`, `is_organic` или `event_type`;
- встречается неизвестный `event_type`.

Некорректные значения `is_organic` подсчитываются в профиле, но в текущем коде
не останавливают сборку.
